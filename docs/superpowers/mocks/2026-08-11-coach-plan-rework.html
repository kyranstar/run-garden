Why reads need their own ledger (not the message thread)

Analyses are currently stored as role:"coach" messages. Automating them as-is would quietly break the coach three ways: every read resets the 20-hour briefing-staleness clock (so the coach would stop briefing), reads crowd the 30-message thread and the wake dossier's 10-message tail, and there's no idempotency constraint — concurrent ingests duplicate reads. So reads move to a coach_reads table, one row per activity.

GuardRule
Idempotencyunique(userId, activityId); re-ingest with a changed fingerprint marks the read stale rather than duplicating it.
Trigger pointEnqueued post-ingest (waitUntil), hourly sweep as catch-up — cap 2 reads/user/tick so cron never stalls on a 600s LLM call.
BackfillOnly activities that started within 14 days of ingest get auto-read. A history backfill gets one batch digest read, not hundreds of calls.
BudgetAuto-reads pause at $12 of the $20/wk rolling budget — interactive coach and studio always keep headroom. ~$0.05/read at the strong tier ≈ $0.40/wk at 8 activities.
FailureAttempt counter + exponential backoff (today a failed analysis leaves no trace and would retry forever).
Kill switchesReads honor prefs.aiEnabled, AI_DEFAULT_ENABLED, fixture mode, and key-presence — the gates the weekly review already has and analysis currently skips.
OutputProse read (as today) plus a ≤90-char glance and structured flags (e.g. hr_drift, breakthrough, strain_high). Flags feed notable_read triggers; glances feed the brief, activity rows, and the dossier.

§6

The weekly brief — concise, or it fails

Week 5 of 12 — on track. Needs you · 1
1 of 6 sessions 40 min of 5 h 05 4-wk adherence 86% ↗ load 7d/28d 1.04
CoachSaturday's 10-miler anchors the week. Sleep ran short last night — I've suggested easing today's tempo; the long run stays.
  1. Headline — a state, not a stat. One of: on track · slightly behind · ahead · rebuilding · race week · resting. Derived deterministically from adherence + load ratio; the garden's voice rules apply — it names the situation, never scolds.
  2. Four chips, no more. Sessions done/planned · time done/planned · 4-week adherence with trend arrow · acute:chronic load ratio. All deterministic, from a new GET /api/plan/week that finally joins planned totals with actuals server-side.
  3. One action line from the coach. The wake's briefing gains a structured focus field — a single sentence that must name the week's anchor and at most one adjustment. It refreshes when the coach wakes; between wakes it stands (stale after 3 days → falls back to the deterministic headline only).
  4. “Needs you” chip only when proposals are pending — tap opens the coach. No pending work, no chrome.
§7

Where the coach lives — three options

A · Floating window recommended

Plan owns the full width; the coach overlays when open, minimizes to a pill. Non-modal — the plan stays interactive behind it.

Why: its most common state is quiet; reserving 40% of the page for an empty panel is today's biggest wart. Ghost-tap → window-open keeps the one-approve-surface rule.

B · Docked rail

Today's layout, tidied: coach always visible in a right column.

Cost: the week grid loses ~340px forever; on 13″ laptops day cells go back to truncating titles. Familiar, but it's the layout the audit flagged.

C · Inline feed

Coach content flows in the page (brief + tray inline under the header); conversation only in a sheet.

Cost: proposals push the calendar down exactly when the coach is busiest; thread loses persistent presence on desktop. Best on mobile — which is why mobile keeps pill + sheet regardless.

§8

What stays, what goes, what's new

Stays untouched

  • Proposal state machine (draft→pending→approved/declined/superseded/expired), guardrails, receipts, undo
  • Workout detail sheet and every mutation (move, match, skip, COROS sync)
  • Memory — store, chips, Settings editor
  • Garden contract — no new writes; sanctionedBy + block-adherence levers unchanged; determinism and resim untouched
  • Design tokens, Sheet/dialog contract, category palette

Goes

  • Month almanac grid (−8/+18 week render) → one pickable week
  • Embedded StudioSection → absorbed by the studio modal
  • Manage-plans sheet → plan cards + modal actions
  • Duplicate CoachPanel mount + idPrefix hack → one mount in the window/sheet
  • “Today” scroll button, extend CTA row → obsolete by construction

New on the server

  • coach_reads table + ingest hook + sweep (§1 guards)
  • GET /api/plan/week — planned vs actual, brief facts
  • Plan detail route — weeks (firm/shape), headline progressions with series
  • focus field on wake output; notable_read trigger; RECENT READS dossier section
  • Coach lift sessions keep structure (exercises JSON survives apply, so coach-authored plans graph too)
§9

Six decisions, then I write the spec

1 · Coach placementFloating window (A) vs docked rail (B) vs inline feed (C). Default: A.
2 · Read model tierStrong (Opus, ~$0.05/read — richest reads) vs cheap (Haiku, ~$0.005). Default: strong while volume is ~8/wk; config knob either way.
3 · Backfilled historySkip old activities entirely vs one batch-digest read per backfill. Default: batch digest — the coach should know your history, cheaply.
4 · Page nameKeep “Plan” vs rename to “Coach”. Default: keep Plan — the page is the plan; the coach lives in it.
5 · Brief chipsMy four: sessions · time · adherence trend · load ratio. Swap any for distance, streak, or a garden tie-in? Default: as mocked.
6 · Studio absorbConfirm retiring the embedded Studio section and Manage-plans sheet into the modal. Default: yes.

On approval: spec → implementation plan → build in slices (server ledger first, page second, modal third), screenshot review before merge as usual. Ping me with edits to any section — mocks regenerate fast.
